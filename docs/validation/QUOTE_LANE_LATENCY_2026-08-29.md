# 报价通道延迟拆解 — 一次被自己的假设推翻的测量

日期：2026-08-29（数据窗口 2026-08-24..28）
提交：`5123da7`
影响：单标的报价 ~50s；合约发现每天重复付费；client id 冲突被报成网络超时

## 问题

批量化（`ccf31a4`，2026-08-15）之后单标的从 ~165s 降到 ~50s。问剩下的 50 秒花在哪。

## 第一次拆解是错的（记录在此，因为错法有价值）

先做的回归是：

```
秒 = -3.5 + 7.94 × 到期数 + 8.21 × 批次数      R² = 0.95
```

据此报告「发现约 24s / 报价约 25s」。**这个拆分不成立。**

批次数是用 `ceil(合约数 / 40)` 算的，40 是 `IB_OPTION_QUOTE_BATCH_SIZE` 的**代码默认值**，
而生产跑的是 90：

```
ecosystem.config.cjs  quantrift-options-quote-worker
  IB_OPTION_QUOTE_BATCH_SIZE: '90'
raw_metadata（生产快照）
  max_contracts_per_expiration: 80    max_contracts: 240
```

90 > 80，所以**每个到期日恰好一批**，批次数就等于到期数。用 `ceil(合约数/40)` 等于把
合约数超过 40 的到期日重复计一次。改用正确规则之后两个自变量直接合并成同一个。

R² 0.95 没有救回任何东西 —— 拟合得好和归因得对是两件事。

## 修正后的拆解

538 个成功任务（2026-08-24..28）：

| 模型 | R² |
|---|---|
| `-4.37 + 20.51 × 到期数` | 0.480 |
| `2.82 + 6.53 × 到期数 + 0.273 × 保留合约数` | **0.874** |
| `1.89 + 12.99 × 到期数 + 0.040 × 发现合约数` | 0.720 |
| `3.17 + 6.59 × 到期数 + 0.249 × 保留 + 0.006 × 发现` | 0.877 |

中位标的 3 个到期、103 张合约 → 约 50s，与实测 p50 吻合。

值得注意：**每合约系数 0.273s,而 `IB_OPTION_CONTRACT_DELAY` 只解释 0.05s**。
大部分时间随「碰了多少张合约」增长,而不是随「发了多少次往返」增长。

## 观测数据无法拆开发现和报价

到期数、梯子大小、保留合约数在标的之间同向变动。任何在观测数据上的拟合都只是在
用同一个变量的不同代理。**所以换成计时,不是换成更好的模型。**

`fetch_option_chain` 现在同时记录:

- `discovery_timings` —— 每个 (到期, C/P) 一条,带 `source: ib | cache`
- `batch_timings` —— `subscribe_seconds` / `quote_ready_seconds` / `oi_ready_seconds` / `wait_seconds`

跑满一个盘中时段即可直接读出拆分,不需要再论证。

## 直接测到的一件事

同一条 AAPL 80 档梯子,2026-08-28 盘中:

```
reqContractDetails   2.12s
registry 读取        0.132s
用重建的 conId 报价   5/5 在 2.896s 内拿到 bid/ask + greeks
```

每标的 6 次这样的调用(3 个到期 × C/P)。梯子在一天之内不变 —— IB 是在现价走到需要时
才挂新行权价,不是持续挂 —— 所以按交易日缓存一次。

`option_contract_registry` 只在**不可能改变选择结果**时使用:梯子横跨整个窗口,或两侧
都已凑满 `max_per_side`。梯子在现价移动的那一侧不够就算 miss,回去问 IB —— 那正是新
行权价会出现的位置。读写全程 best-effort,没库、没表、梯子可疑都退化成改动前的行为。
命中/未命中数写进 `raw_metadata`。

按交易日生效,所以每天第一轮必然全 miss,这是设计。

## 没做的事

**没有缩短批次等待窗口。** `has_analysis_payload` 把 OI 也算进完成条件,而 OI 是日频数字、
走 IB 的慢 tick 节奏、盘中不会变 —— 批次可能为了一个「超时也照样落库」的数字把窗口占满。
把有/无 OI 缺失的快照分组回归,单批 9.70s vs 8.21s,只差 1.5s,**所以不是个别流动性差的
合约掉队,是 OI tick 本身就晚**。收益多少不猜,`quote_ready_seconds` 会直接给出答案。

**没有动任何阈值或间隔。**

## 附带修掉:错误 326 被吞掉

client id 重复时 IB 在 reqId -1 上回 error 326。`error()` 记进了 `error_msg`,`_connect`
把它丢掉,只抛一句 `IB connection timed out` —— 一个既不是网络也不是超时的问题,却报成
网络形状。2026-08-28 因此花了 110 分钟才定位:id 42 连不上,而 44 / 47 / 91 各 0.00s 连上。

现在实测:

```
IB connection timed out: 127.0.0.1:4001 client_id=42
  (IB error 326: Unable to connect as the client id is already in use. Retry with a unique client id.)
```

**326 不是当天故障的全部。** 换干净 id 之后 `reqContractDetails` 正常而
`reqSecDefOptParams` 20s 超时,AAPL 和 SPY 都是 —— 只修 client id 每次取链还是会死在
下一个调用。两个故障后来都自行恢复。

## 教训

1. **代码默认值不是生产值。** 派生变量之前先去 `ecosystem.config.cjs` 和生产
   `raw_metadata` 核对实际配置,否则整个自变量就是错的。
2. **R² 高不等于归因对。** 共线的代理量能拟合得很好,同时把因果说反。
3. **观测数据拆不开的东西,加个计时器就拆开了。** 与其在数据上再拟合一次,不如让代码
   自己报时间。

## 追加 2026-09-02:计时点上线后的实测,以及缓存作用域的设计错误

计时点跑了两个交易日,结论如下。

### 成本归属(直接计时,不再是回归)

中位任务 54.7s:

| 阶段 | 秒 | 占比 | 实测关系 |
|---|---|---|---|
| 合约发现 | 22.1 | 40% | `3.35 + 0.014 × 梯子大小` 每次往返,6 次/标的 |
| subscribe | 19.9 | 36% | `0.193 × 合约数`,R²=0.992 |
| batch wait | 7.5 | 14% | 其中约 4.9s 是 OI 缺席的批次 |
| 其余 | ~5.0 | 10% | 连接 / 现价 / secdef / 落库 |

上一节说「观测数据拆不开」,所以换成计时——现在拆开了。发现约 22s 这个量级,
和最初那个被撤回的回归**在数量级上碰巧接近**,但那次是靠共线代理量凑出来的,
这次是钟表读出来的。**结论对不代表推导对。**

### 缓存两天命中 2 次:作用域定错

```
08-31   724 次查询 / 1 次命中 / miss 全是 no_rows / 写入 45,721 行
09-02   729 次查询 / 1 次命中
```

写入正常。**141 个标的每天各访问恰好 1 次**,而缓存作用域是「一个交易日」——
读必然发生在那个标的当天唯一一次写之前。按天过期是叠在充分性规则上的第二层保险,
而它吃掉了 100% 的收益。

修法:改成「backstop 窗口内最新一条梯子」,正确性交给两条检查:

1. **`reqSecDefOptParams` 的实时行权价集合**(每次取链本来就请求,零额外成本)。
   这是跨天安全的关键:**拆股不是在边缘加价位,是整条梯子替换**,而旧 conId 仍能
   解析成调整后的非标准合约——会报出**别的东西的合理数字**。这是几何规则唯一看不见、
   且比「报不出来」更糟的漂移。比对带容差(IB 线格式 ↔ `NUMERIC(18,4)` 不精确往返,
   严格相等会静默关掉缓存)。没有实时集合时**跳过而不是假设**。
2. 原有几何规则不变。

`IB_OPTION_CONTRACT_CACHE_MAX_AGE_DAYS=30` 只是兜底。

实测:SNDK 梯子 0.198s / 328 行,之前同一次读返回空。

### OI 的机制我说反了

```
quote_ready p50 = 0.950s      oi_ready p50 = 0.925s      ← 几乎相同
OI 到齐的批次   n=221  wait 均值 1.012s
OI 未到齐的批次 n=137  wait 均值 6.083s   ← 吃满窗口
```

**不是「tick 晚」,是「压根不来」。** 来的时候和报价一起来。成本全在那 137 批。
移出完成判据值约 4.9s/标的(9%)——方向对,机制错。

### subscribe 才是第二大项,而且大部分不是我们的 sleep

```
subscribe_seconds = 0.001 + 0.1926 × 合约数     R² = 0.992
IB_OPTION_CONTRACT_DELAY = 0.05  只解释 26%
```

其余 0.14s/合约 是 `reqMktData` 本身(ibapi 串行写 socket + IB 入站限速)。
所以调 delay 最多省 19.9s 里的 5.2s,真正的杠杆是**减少合约数**,不是加快订阅。

### 补一条教训

4. **一个缓存要先对得上访问模式,再谈正确性。** 充分性规则设计得再严谨,
   作用域配不上「每标的每天一次」的访问节奏,命中率就是 0.1%。
   **上线后必须回读命中率**——它不会自己报错。
