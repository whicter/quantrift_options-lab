# 报价来源的采购决策依据（2026-08-09）

`OPTION_QUOTE_COVERAGE_2026-08-09.md` 已确认「Polygon 期权档不含报价、覆盖率 1/327、调度器已补齐」。
本文只补它没有的一件事：**要不要花钱，花在哪**。三条路各自的实测边界。

## 一、Massive（原 Polygon）档位:报价只在 $199 那档

实测 2026-08-09（`massive.com` 定价页 Options 标签）：

| 档位 | 月费 | **Quotes** | Trades | 延迟 | 历史 |
| --- | --- | --- | --- | --- | --- |
| Basic | $0 | ✗ | ✗ | 仅收盘 | 2 年 |
| **Starter（当前）** | **$29** | **✗** | ✗ | 15 分钟延迟 | 2 年 |
| Developer | $79 | **✗** | ✓ | 15 分钟延迟 | 4 年 |
| **Advanced** | **$199** | **✓** | ✓ | 实时 | 5+ 年 |

**没有中间档。** $79 的 Developer 加的是 Trades 而**不是 Quotes**，所以想解决候选定价，
只能从 $29 直接跳到 $199（+$170/月，$2,040/年）。任何"升一档试试"的方案都不存在。

API 侧的佐证（单合约快照返回的键）：

```
['day', 'details', 'greeks', 'implied_volatility', 'open_interest', 'underlying_asset']
```

`last_quote` / `last_trade` **连键都不出现**。这与"延时"是不同的失败形态：
延时数据会有键、时间戳旧 15 分钟；**键缺失是权限层面整块剥离**。
判断某档是否含报价时应看键是否存在，不要用"现在是不是休市"解释。

## 二、IB:权限没问题，瓶颈是我们自己的串行实现

### 权限已确认（此前只由"存了 44 行"间接推断）

对 SPY 2026-09 CALL 直接 `reqMktData` 实测，**零订阅错误**——没有 `354`（未订阅）
也没有 `10167`（仅延时可用），并收到 close tick。休市时 bid/ask 返回 `-1` 是无报价流，不是无权限。

同时实测生产中报过超时的那个原始请求：

| 请求 | 结果 | 耗时 |
| --- | --- | --- |
| PLTR / SPCX / SPY 股票合约 | OK | 0.17–0.36 s |
| **PLTR 2026-09-04 CALL 链** | **OK，90 个合约** | **2.38 s** |

超时阈值是 30 秒。**IB 侧没有系统性问题**，SPCX 也是有效标的。

### 吞吐上限来自代码，不是 IB

`ib_option_chain_provider.py` 的报价阶段严格串行，一次一个合约：

```python
for contract in selected_contracts:
    contracts.append(self._fetch_contract_snapshot(app, contract, symbol))  # 逐个等
    time.sleep(self.contract_delay)   # 默认 0.05
```

叠加 `QUOTE_WORKER_CONCURRENCY=1`（IB 固定 clientId 并发会冲突），整条链路完全串行。
IB 标准账户有上百条并发行情线路，**我们只用一条**。

按生产参数（`OPTION_MAX_CONTRACTS=240`、间隔 0.05 s、盘中单合约响应约 0.1–0.3 s）估算：

| 覆盖目标 | 单轮耗时 | 390 分钟交易日内轮数 |
| --- | --- | --- |
| 50 标的（当前 `quote_watchlist`） | 约 50–100 分钟 | **4–7 轮，够用** |
| 327 标的（全 `scan_enabled`） | 约 5.5–11 小时 | **一轮都跑不完** |

**结论：IB 结构上服务得了几十个标的，服务不了全市场。** 这不是 IB 的限制，是当前实现的限制；
并行化在理论上可行，但要处理 clientId 冲突、行情线路配额、报文速率限制与失败隔离，
并直面本仓库已记录的 IB 脆弱性（socket 假死、超时占通道）。

| --- | --- | --- | --- |

**三次失败在休市时段**，正是市场时段门要挡掉的形态。两次盘中尝试里一次成功，
另一次（PLTR）的同一请求今日实测 2.38 秒完成，属瞬时问题（IB 报文限速，

`unsupported job_type=option_quote_snapshot` 那条是 **07-30 22:40**，即引入 quote worker 当天，
属切换期遗留，**不是仍然存在的缺陷**——不要据此再去排查 worker 的 job_type 分发。

## 四、一个会浪费时间的读日志陷阱

`quantrift-quote-refresh` 休市时输出：

```
{'status': 'market_closed', 'watchlist': 0, 'enqueued': 0}
```

`watchlist: 0` **不代表清单为空**。它来自 `run()` 的市场时段提前返回，该分支根本没有查库，
硬编码返回 0。实测 `quote_watchlist` 表有 **50 行、0 个 excluded**。
判断清单是否为空要看 `status`：`empty_watchlist` 才是真的空，`market_closed` 只是没看。

## 五、第三方 flow 供应商:整个类别不可用

| 供应商 | 月费 | 结论 |
| --- | --- | --- |
| Unusual Whales | API $150 / Advanced $375 | **仅限个人使用，禁止再分发**，违规终止账户且不退款并可能追责 |
| Bullflow.io | 平台 $39 / API $99 | **仅限个人使用**，商用需另谈 |

两家条款一致：授权范围是"个人或公司内部使用"，明确禁止提供给第三方。
Quantrift 有订阅分层与 Stripe 计费，向付费用户呈现即构成再分发。
**这与本文档 Short Squeeze 一节对 FINRA 的结论逐字同构**（"本项目有订阅分层，直接违反"），
当时的解法是走已持有转授权的 Polygon。

结构性原因值得记住：**UW / Bullflow 这类是分析产品，不是数据授权商。**
分析产品卖"给你看"，数据授权商卖"你可以再分发"。订阅制产品只能买后者，
所以这个类别不必再逐家评估。

覆盖面上它们也不构成替代：Bullflow 只有 flow alerts，无期权链、无 K 线、无参考数据；
UW 的历史 K 线要另走 Data Shop，且两家都没有全市场 grouped daily 与 ticker 参考元数据。

## 六、尚未澄清的授权问题（比档位选择更要紧）

Massive 全部期权档位标注 **"Individual use"**，Advanced 另标 **"Non-pros only"**，
页面另设 "View business pricing" 入口。

Quantrift 有订阅分层与计费，属商业用途。**这意味着不论升不升级，当前 $29 档的授权范围本身需要核实**——
若个人档不覆盖商业使用，真实价格是 business 档而非 $199。

注意这与 `OPTION_QUOTE_COVERAGE_2026-08-09.md` 的「授权立场（推迟，非解除）」是同一条线：
产品负责人已确认当前内部阶段可用 IB/TT，但**认证、订阅或公开上线任一项落地即重新生效**。
向 Massive 销售确认的问题应当一次问全：订阅制产品向付费用户展示**自算衍生结果**
（GEX、候选腿），而非原始链，需要哪一档授权。

## 七、决策状态:等周一实测，不要现在买

三条路缺同一个输入——**IB 通道在真实盘中的表现，它一次都还没跑过**
（`quantrift-quote-refresh` 排程 `*/10 7-12 * * 1-5`，2026-08-09 是周日）。

周一盘中一轮即可得到：每标的实际耗时、盘中失败率、实际覆盖标的数。据此：

- IB 稳定覆盖 50 标的 → 是否够用是**产品定位问题**（精选深度 vs 全市场扫描），不是数据问题；
  可先零成本上线，有收入再升级。中间选项：把 `QUOTE_WATCHLIST_TARGET` 由 50 上调试探。
- IB 太慢或盘中失败率高 → $199 Advanced 有了实测依据，且顺带解决 Mac Studio 单点与串行上限。

**在实测之前采购，是为一个尚未测量的缺口付钱。**
